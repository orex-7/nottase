# Plano — Inserir 100 mil linhas de teste num database (para validar a virtualização)

## Objetivo
Popular um database com ~100.000 linhas para validar manualmente a virtualização
da visão Tabela (nós no DOM, fluidez do scroll, edição/drag/seleção).

## ⚠️ Avisos obrigatórios (ler antes)
1. **Nunca em produção.** Use Supabase **local** (`supabase start`) — recomendado — ou
   um projeto **de teste** dedicado. Apague os dados depois.
2. **O app não pagina.** `fetchDatabases()` (`src/lib/database.ts:91-106`) busca
   `database_rows` numa única query, ordenada por `position`/`created_at`. O PostgREST
   limita a resposta em `max_rows` (`supabase/config.toml:18`, hoje **1000**).
   **Consequência:** com 100k linhas no banco, a UI carrega só 1000 até você **subir
   `max_rows`** no local (ex.: `200000`) e **reiniciar** o Supabase. Sem isso, o teste
   de virtualização continua válido, mas com ≤1000 linhas.
3. **RLS**: as policies exigem `user_id = auth.uid()`. Inserir por SQL como `postgres`
   (local) ou com a `service_role` (teste) **ignora a RLS** — use apenas local/teste.

## Pré-condições
- Supabase local no ar: `supabase start` → API `http://127.0.0.1:54321`,
  Studio `http://127.0.0.1:54323`, DB `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.
- `.env` apontando para o local (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`)
  e `npm run dev`.
- Um database criado pela UI (para ter `columns` válidas).

## Passos
1. Subir o Supabase local e o app:
   `supabase start` → conferir `.env` → `npm run dev`.
2. Logar (Google) e criar um **database** de teste pela UI.
3. Descobrir `database_id`, `user_id` e os **ids das colunas**:
   ```sql
   select id as database_id, user_id, columns
   from public.databases
   order by created_at desc
   limit 1;
   -- (se precisar do usuário: select id from auth.users order by created_at desc limit 1;)
   ```
   `columns` é `[{ id, name, type }, ...]` — `values` é indexado por **`column.id`**.
4. Inserir as linhas — **Opção A (recomendada): SQL** no SQL Editor do Studio local
   (ou `psql "<DB URL>"`). Ajuste os UUIDs e as chaves de `values`:
   ```sql
   insert into public.database_rows (database_id, user_id, values, position)
   select
     '<DATABASE_ID>'::uuid,
     '<USER_ID>'::uuid,
     jsonb_build_object(
       '<COLUNA_TEXTO_ID>',   'Item ' || g,
       '<COLUNA_STATUS_ID>',  (array['todo','doing','done'])[1 + (g % 3)]
       -- adicione outras colunas se quiser (número, data, checkbox...)
     ),
     g
   from generate_series(0, 99999) as g;
   ```
   - 100k num único `INSERT` funciona; se preferir, faça em blocos (ex.: `g` de 0..9999
     repetido 10x trocando o `position` base).
   - `position` não tem constraint de unicidade — usar `g` dá ordenação determinística.
5. Conferir a contagem:
   ```sql
   select count(*) from public.database_rows where database_id = '<DATABASE_ID>';
   ```
6. **Deixar a UI enxergar tudo** (senão ela corta em 1000): em `supabase/config.toml`,
   em `[api]`, mudar `max_rows = 200000` e reiniciar (`supabase stop` e `supabase start`).
7. Abrir o database no app (visão Tabela) e validar.

### Opção B — script Node com `service_role` (projeto de teste)
Criar um script temporário (fora do app) que insere em lotes de ~5.000 usando
`@supabase/supabase-js` com a **service_role key** e um `insert([...])` em massa.
Útil quando não se quer usar `psql`. Mesmos UUIDs e mesma forma de `values`.

### Opção C — `supabase/seed.sql` (reprodutível)
`config.toml:70` já aponta `db.seed.sql_paths = ["./seed.sql"]` (arquivo **inexistente**).
Criar `supabase/seed.sql` com o `INSERT` do passo 4 → `supabase db reset` semeia
automaticamente. **Atenção:** `db reset` **recria o banco local** (apaga dados locais).

## Limpeza (depois do teste)
```sql
delete from public.database_rows where database_id = '<DATABASE_ID>';
-- ou: delete from public.databases where id = '<DATABASE_ID>';  -- remove em cascata
```

## Validação manual (o que observar)
- Elements → `<tbody>`: poucas `<tr>` (~visíveis + 2×overscan + 2 spacers), **não** 100k.
- Scroll vertical/horizontal fluido; cabeçalho fixo; sem "pulos".
- Editar célula e rolar: o input mantém foco/estado.
- Menu de célula aberto + rolar: continua ancorado.
- Arrastar linha até a borda (auto-scroll) e soltar; indicador aparece.
- "Selecionar tudo": marca todas (não só as renderizadas).
- Com busca/filtro, criar linha → aparece e recebe foco.

## Riscos / limitações
- `max_rows` (passo 6) é o motivo mais provável de "só apareceram 1000 linhas".
- 100k linhas vêm numa única resposta JSON e ficam em memória: valida a **renderização**,
  mas o gargalo de **dados** permanece (follow-up: paginação por cursor).
- Inserir como `postgres`/`service_role` ignora RLS — não replicar em produção.
- Rodar `supabase db reset` (Opção C) apaga os dados locais.

## Fora de escopo
- Mudar a camada de dados/`fetchDatabases()` ou adicionar paginação.
- Popular produção.
